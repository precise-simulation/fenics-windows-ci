# Phase 1: prove TinyCC compatibility

**Status:** proposed.

## Objective

Prove that a pinned x86-64 Windows TinyCC build can compile and load the CFFI extension generated by FFCx, then run the existing Poisson solve, without Visual Studio, host Windows SDK compiler inputs, LLVM-MinGW, GCC, or another linker participating in the JIT process.

This is the primary functional, ABI, CRT, and PE-security go/no-go phase. Phase 1 may use a deliberately narrow prototype adapter; production CFFI/setuptools integration is completed in Phase 2.

## Baselines

Test both:

1. latest formal TinyCC Windows x86-64 release, for reference;
2. a checksum-pinned current upstream development commit, expected to contain newer Win64/PE fixes.

If only the development revision passes, document exactly which upstream changes are required and pin that commit for all later phases.

## Compiler adapter prototype

Do not force TinyCC through setuptools' `mingw32` backend.

Prototype the smallest adapter required to prove the compiler path:

- compile generated `.c` with TinyCC;
- prefer direct `tcc -shared <generated.c> ... -o <module.pyd>` source-to-PYD compilation;
- use TCC-owned intermediate objects only if CFFI/build_ext evidence proves an object split is actually required;
- translate include dirs, macros, library dirs, and supported extra arguments;
- reject unsupported options and foreign binary inputs instead of silently ignoring important semantics;
- prevent native-Windows setuptools behavior from adding MSVC/versioned-Python library inputs.

Prefer an owned temporary `build_ext` command whose `build_extension()` directly invokes TinyCC for the CFFI `Extension`. Do not implement a general-purpose `CCompiler` abstraction or depend on `new_compiler("tinycc")` unless the direct build_ext path proves insufficient.

CFFI's current `ffiplatform._build()` creates its own `_shimmed_dist_utils.Distribution`, calls `parse_config_files()`, invokes `run_command("build_ext")`, and then consumes `get_outputs()`. There is therefore no ordinary caller-supplied `cmdclass` injection point to assume. Phase 1 must identify and prove the exact process-local interception used by the prototype. Prefer temporarily replacing `cffi._shimmed_dist_utils.Distribution` with an owned subclass under the activation lock so the `Distribution` created by CFFI installs `TinyCCBuildExt` itself. The subclass must also own the configuration-file policy described below. If the qualified CFFI version makes that interception unreliable, use the narrowest version-pinned wrapper around `cffi.ffiplatform._build()` instead and record why.

TinyCC's Windows `-c` path emits ELF intermediate objects, so do not treat those objects as normal COFF interchange objects.

The prototype may patch only the minimum process-local CFFI/setuptools entry points required for the proof. Record every temporary hook so Phase 2 can replace the prototype with the production owned adapter and activation contract.

### External distutils/setuptools configuration isolation

Hermetic compiler selection must not depend on user, repository, or machine-level distutils/setuptools configuration.

Because CFFI currently calls `Distribution.parse_config_files()` before `build_ext`, the TinyCC interception must either:

1. suppress external config parsing for the owned temporary CFFI `Distribution`; or
2. parse only a deliberately empty/owned configuration source and prove no external option can alter compiler selection, build directories, libraries, library directories, or link flags.

Do not merely sanitize environment variables and then allow arbitrary `setup.cfg`, `pydistutils.cfg`, or equivalent setuptools/distutils configuration to participate.

Add a hostile-config proof that places compiler/build_ext/library options in the configuration locations exercised by the qualified CFFI/setuptools pair and verifies that:

- the owned TinyCC `build_ext` is still selected;
- no external compiler executable or library root is introduced;
- output/cache paths remain the owned paths;
- the configuration is ignored or rejected deterministically rather than partially applied.

## C language/FFCx flags

FFCx 0.11 requests C17 on Windows using `-std:c17`. Current TinyCC development sources expose C11/gnu11 as their newest explicit language mode and otherwise use older C semantics.

For TinyCC:

- treat C11/default TinyCC mode as the known starting point rather than looking for a nonexistent direct `-std=c17` equivalent;
- compile the exact generated FFCx/CFFI corpus and identify whether it uses any semantics not accepted/correctly implemented by the pinned TinyCC revision;
- remove/translate MSVC- or Clang-specific flags;
- preserve `-D__STDC_NO_COMPLEX__` for the initial proof;
- use `-mms-bitfields` by default for the Windows backend unless the ABI proof demonstrates that every cross-compiler interface is unaffected by bitfield layout;
- define `Py_NO_LINK_LIB` only where the active CPython headers support that switch;
- capture the complete generated C source for every failure;
- treat actually required unsupported C17 semantics as a go/no-go result, not as a reason for broad generated-source rewriting.

## Python Stable ABI

Use the same conceptual ABI strategy as LLVM-MinGW: generated modules import `python3.dll` and must not acquire a minor-version Python dependency through setuptools or CPython headers.

TinyCC's Windows linker supports import definition files directly. Generate/package a deterministic `python3.def` from a supported `python3.dll` export set and pass it explicitly to TinyCC.

The integration must own Python-library selection end-to-end:

- override/suppress setuptools `build_ext.get_libraries()` behavior that would otherwise add `python312`, `python313`, `python314`, or another versioned Python library;
- prevent native-Windows setuptools library-directory injection from becoming an accidental source of Python/MSVC link inputs, retaining only explicitly approved roots;
- record whether TinyCC defines `_MSC_VER`, whether CFFI is using `Py_LIMITED_API`, and whether the active CPython headers support/use `Py_NO_LINK_LIB`;
- recognize that CPython's pragma-based automatic Python library linking is conditioned on `_MSC_VER`, so `Py_NO_LINK_LIB` is a defense-in-depth control rather than the primary correctness mechanism for normal TinyCC builds;
- for every supported interpreter, prove the absence of header-driven/versioned Python linking through captured compiler/linker inputs and final PE imports;
- pass packaged `python3.def` to TinyCC explicitly;
- reject any versioned Python library name reaching the TinyCC adapter rather than silently accepting it.

Acceptance checks:

- CFFI wrapper compiles with official CPython headers;
- `.pyd` loads on standard GIL-enabled CPython 3.12, 3.13, and 3.14;
- captured compile/link inputs contain no versioned Python library request;
- PE import inspection shows `python3.dll`, not a minor-version DLL;
- the same definition strategy works for all supported interpreters;
- diagnostics record `_MSC_VER`, `Py_LIMITED_API`, and `Py_NO_LINK_LIB` state for the active interpreter.

Preview standard GIL-enabled Python 3.15 only after the supported matrix passes. The preview is informational/non-blocking until Python 3.15 is promoted into the supported repository matrix. Free-threaded Python is out of scope for this epic unless it is later added as a separate ABI/import-library qualification target.

## Windows ABI and CRT proof

Record generated-module imports and compare with the LLVM-MinGW reference.

Current upstream TinyCC Win64 links `msvcrt.dll` by default. Treat this as a known Phase-1 issue. Before Phase 2 begins, choose and prove one of these outcomes:

1. **Preferred if practical:** configure/patch the pinned TinyCC runtime so generated modules use the required UCRT-compatible model; or
2. **Mixed-CRT qualification:** retain TinyCC's `msvcrt.dll` runtime but prove that no unsafe ownership or representation crosses between TinyCC-generated code and UCRT/MSVC-built CPython/DOLFINx.

Add an ABI probe compiled by MSVC/LLVM-MinGW and TinyCC that records:

- `sizeof` and alignment of relevant UFCx structs;
- offsets of fields read by DOLFINx;
- function-pointer/calling-convention assumptions;
- sizes/alignment of core integer/pointer/floating types used by UFCx;
- explicit `sizeof(long double)` / `alignof(long double)`;
- representative `#pragma pack`/packed-layout behavior used by consumed headers;
- representative bitfield layouts under TinyCC's default behavior and `-mms-bitfields`, compared with the MSVC/LLVM-MinGW consumer contract.

Current x86-64 TinyCC sources define `long double` as 16 bytes with 16-byte alignment, while the normal MSVC Windows ABI does not use that representation. Treat this as a **known ABI mismatch**, not merely a generic probe: if any `long double` object/value crosses the TinyCC-generated UFCx/CFFI boundary into MSVC/UCRT-built consumers, Phase 1 fails unless exact compatible marshaling/representation has been independently demonstrated. If `long double` is absent from every cross-compiler interface, retain a regression check proving that absence.

The qualification outcome must record whether `-mms-bitfields` is mandatory backend policy. Unless the proof establishes that bitfields are absent from every relevant cross-compiler ABI surface, retain it as a required Windows adapter flag.

For a mixed CRT, audit and stress any memory, FILE/handle, locale, errno, allocation, string, and error-path ownership that crosses the extension/native boundary. Use Python allocator APIs where generated CFFI wrappers already do so, but do not infer mixed-CRT safety merely from one successful Poisson run.

## PE security and unwind proof

Inspect the emitted `.pyd` beyond import/load success.

The required x86-64 baseline is fixed before testing:

- `IMAGE_DLLCHARACTERISTICS_DYNAMIC_BASE` set;
- `IMAGE_DLLCHARACTERISTICS_HIGH_ENTROPY_VA` set;
- `IMAGE_DLLCHARACTERISTICS_NX_COMPAT` set;
- usable base relocation metadata present and consistent with ASLR;
- x64 `.pdata`/unwind/exception metadata present and valid for generated functions according to the qualification probe.

For representative minimal CFFI and FFCx modules, record and compare with LLVM-MinGW:

- full PE `DllCharacteristics`;
- relocation directory presence/consistency;
- x64 `.pdata`/unwind metadata coverage;
- imported system DLLs and unexpected legacy/runtime dependencies.

Current TinyCC x86-64 defaults may leave `DLLCHARACTERISTICS` at zero, but current TinyCC exposes PE linker controls for dynamic base, high-entropy VA, and NX compatibility. Phase 1 must therefore proceed in this order:

1. emit a baseline image and record its defaults;
2. retry with the supported TinyCC linker controls for dynamic base, high-entropy VA, and NX compatibility;
3. verify the required mitigation bits, relocations, unwind metadata, and load behavior;
4. require a small pinned source patch only if supported linker controls cannot produce the fixed baseline.

If the fixed hardened x64 PE baseline cannot be maintained with supported options or a narrow maintainable patch, stop the epic.

## Object/library boundary

TinyCC's Windows `-c` path emits ELF objects and is not a normal MSVC/MinGW COFF interchange surface. Direct source-to-PYD compilation is preferred so this format remains an internal implementation detail rather than a public adapter contract.

The prototype must reject unsupported foreign link inputs explicitly, including:

- `.lib` files;
- foreign `.obj`/`.o` files;
- arbitrary `.a` archives not produced/qualified for the packaged TinyCC;
- unsupported `extra_objects`;
- arbitrary `cffi_libraries` requests that cannot be satisfied through an approved import mechanism.

Known packaged Python/system `.def` imports and, only if unavoidable, TCC-owned objects/archives are the explicit non-source path. Add at least one negative test in Phase 1 so accidental future pass-through cannot masquerade as support.

## System-library policy

Native TinyCC can add the Windows system directory to its library search path and resolve system DLLs directly. Treat this as an explicit operating-system input, not as an accidental ambient-development dependency.

Phase 1 must choose and document one of these policies:

1. **Approved system-DLL lookup:** allow only normal Windows system directories for runtime/system DLL resolution, record those roots and final PE imports, and reject host SDK import-library/development directories; or
2. **Fully explicit definitions:** disable implicit library search where practical and provide the required packaged/approved system definitions explicitly.

In either case:

- Visual Studio, Windows Kits/SDK library directories, Python `libs`/`PCbuild`, and arbitrary ambient library paths are forbidden;
- the final PE import table is authoritative for what system/runtime dependencies were introduced;
- diagnostics must distinguish allowed OS DLL resolution from forbidden SDK/compiler-development inputs.

## Hermetic proof environment

Reuse the LLVM-MinGW sanitization approach:

- clear VS/MSVC/Windows SDK activation variables;
- remove Visual Studio and Windows Kits paths from `PATH`;
- clear `CC`, `CXX`, `LD`, include/library search variables;
- expose only the TinyCC package/prototype root, active Python/FEniCS runtime DLL paths, approved Windows system directories, and any explicitly approved definition roots;
- clear the TinyCC-specific backend-cache identity namespace before each fresh JIT.

CI must fail if the JIT invokes or resolves `cl.exe`, MSVC `link.exe`, Clang, GCC, `vswhere.exe`, or host Windows SDK development inputs.

## Tasks

1. Add a manual-only TinyCC experiment workflow on `windows-2022`.
2. Pin and build/download the selected TinyCC x86-64 revision.
3. Implement the smallest prototype TinyCC `build_ext` adapter, preferring direct source-to-PYD compilation and proving the exact CFFI `Distribution` interception point.
4. Neutralize external CFFI/setuptools/distutils configuration for the owned TinyCC `Distribution` and add a hostile-config regression proof.
5. Compile/import a minimal CFFI module.
6. Implement the `python3.def` Stable-ABI link path and suppress all implicit versioned Python linking.
7. Translate/reject FFCx compile flags explicitly, including the qualified Windows bitfield-layout flag, and prove the generated corpus under TinyCC's available language modes.
8. Run a fresh FFCx Poisson JIT/solve on standard GIL-enabled CPython 3.12-3.14.
9. Run ABI layout probes against the LLVM-MinGW/MSVC reference, including packing/bitfields and the known `long double` mismatch.
10. Establish either UCRT-compatible TinyCC output or a documented mixed-CRT safety proof.
11. Qualify explicit TinyCC PE hardening linker options against the fixed x64 baseline before considering any source patch.
12. Inspect PE imports, mitigations, relocation/unwind metadata, and retain compile/link/source diagnostics.
13. Establish and test the explicit system-library-resolution policy.
14. Add negative foreign-object/library-input tests.
15. Preview standard GIL-enabled CPython 3.15 as non-blocking evidence.

## Exit criteria

Phase 1 passes only when all supported Python versions compile, load, and solve correctly with TinyCC as the sole JIT compiler/linker; the exact owned CFFI interception path is demonstrated; external distutils/setuptools configuration cannot alter compiler selection or link inputs; generated modules import only the intended Stable-ABI Python DLL; no implicit/versioned Python library input participates; the C language, Python/UFCx ABI, packing/bitfield policy, known `long double` mismatch, CRT model, fixed PE mitigation/unwind baseline, system-library policy, and object/library boundary are demonstrated; and no required generated C feature is unsupported.

If this phase needs invasive FFCx source rewriting, cannot establish a safe CRT/ABI boundary, exposes incompatible `long double` across the compiler boundary, cannot produce the fixed hardened PE image with supported options or a narrow maintainable change, or requires foreign object/library interoperability that TinyCC cannot provide, stop the epic.
