# Phase 1: prove LLVM-MinGW compatibility

**Status:** compatibility proof passed; packaging remains Phase 2.

## Objective

Prove that an unmodified upstream LLVM-MinGW UCRT x86-64 toolchain can compile and load the CFFI extension generated by FFCx, and then run the existing Poisson solve, without using MSVC or the host Windows SDK.

This is the primary functional go/no-go phase.

## Environment

Use the GitHub-hosted `windows-2022` runner.

Start from an upstream LLVM-MinGW UCRT x86-64 distribution. The runner has Visual Studio installed, so the proof must deliberately make it unavailable to the JIT process and verify the actual compiler/linker inputs.

Before each fresh JIT:

- do not enter a VS developer shell;
- replace `PATH` rather than inheriting compiler paths;
- clear Visual Studio activation variables, including `VSINSTALLDIR`, `VCINSTALLDIR`, `VCToolsInstallDir`, and `VSCMD_*`;
- clear `INCLUDE`, `LIB`, `LIBPATH`, `WindowsSdkDir`, `WindowsSDKVersion`, `UniversalCRTSdkDir`, and `UCRTVersion`;
- ensure `cl.exe` and MSVC `link.exe` are not resolvable;
- expose only the packaged LLVM-MinGW toolchain plus required FEniCS/Python runtime directories;
- provide no MSYS2 fallback;
- clear the FFCx JIT cache.

A PowerShell setup should be equivalent in intent to:

```powershell
$env:PATH = "$jitBin;$prefix;$prefix\Library\bin;$prefix\Scripts;$env:SystemRoot\System32;$env:SystemRoot"

$remove = @(
    "VSINSTALLDIR", "VCINSTALLDIR", "VCToolsInstallDir",
    "INCLUDE", "LIB", "LIBPATH",
    "WindowsSdkDir", "WindowsSDKVersion",
    "UniversalCRTSdkDir", "UCRTVersion"
)
$remove | ForEach-Object {
    Remove-Item "Env:$_" -ErrorAction Ignore
}
Get-ChildItem Env: |
    Where-Object Name -Like "VSCMD_*" |
    ForEach-Object { Remove-Item "Env:$($_.Name)" -ErrorAction Ignore }
```

## Compiler backend selection

CFFI delegates compilation to setuptools/distutils `build_ext`. On Windows this normally selects MSVC.

The direct `cffi.FFI.compile()` path used by FFCx does not expose a compiler-backend argument. Setting `CC` alone is insufficient because it only changes the executable after a GNU-style compiler backend has been selected.

The first prototype should use JIT-local setuptools configuration, conceptually:

```ini
[build_ext]
compiler = mingw32
```

with process-local:

```text
CC = <runtime>/bin/x86_64-w64-mingw32-clang.exe
```

CFFI changes into its temporary build directory before creating the setuptools `Distribution`, whose `parse_config_files()` path is used by `build_ext`. Verify this behavior against the exact CFFI/setuptools versions used by the packages.

If JIT-local `setup.cfg` is not deterministic, use a small owned integration patch/helper that sets `build_ext.compiler = "mingw32"` programmatically.

Do not depend on:

- a user's global `setup.cfg`;
- shell activation;
- registry configuration;
- global Python compiler replacement.

Preferred implementation order:

1. verified JIT-local setuptools backend selection plus process-local `CC`;
2. small FFCx/CFFI integration patch that sets the backend programmatically;
3. narrow custom compile/link adapter if setuptools selection proves too fragile.

CI must record both the selected compiler type (`mingw32`) and the actual compiler/linker executables.

## FFCx compile flags

Current Windows FFCx may emit MSVC-style C17 flags:

```text
-std:c17
```

GNU-driver Clang requires:

```text
-std=c17
```

Fix compiler flags before the first Poisson JIT. Flags must depend on the selected compiler backend rather than only `sys.platform`.

Prefer an upstreamable FFCx fix; otherwise carry a small documented package patch.

## CPython headers and import libraries

CFFI JIT needs:

- matching CPython headers, including `Python.h` and `pyconfig.h`;
- a GNU/LLVM-MinGW-compatible Python import library.

CFFI already attempts to use `Py_LIMITED_API` for ordinary CPython 3 Windows extensions where permitted. The main unresolved issue is the library selected by setuptools' MinGW link step.

On official Windows CPython, setuptools `build_ext.get_libraries()` adds a versioned Python library such as `python312`, `python313`, or `python314` for a non-MSVC compiler.

Evaluate:

1. **Preferred stable-ABI path**
   - retain CFFI's limited-API wrapper;
   - ensure the resulting PE extension imports `python3.dll`;
   - either override the JIT-local setuptools Python-library selection to request `python3`, or provide version-named GNU import libraries (`libpython312.a`, etc.) whose import descriptors deliberately target `python3.dll`.
2. **Fallback versioned path**
   - generate a GNU import library for the active interpreter DLL;
   - select the matching library per CPython runtime;
   - do not allow the package to silently bind to only the build-time interpreter.

Generate import libraries during package construction/prototyping and do not retain `llvm-dlltool` in the final runtime solely for this purpose.

Inspect the generated `.pyd` PE import table. For the stable-ABI strategy, the acceptance condition is an actual `python3.dll` import.

## Diagnostics

Log and retain:

- selected setuptools compiler backend;
- compiler and linker command lines;
- Clang effective include paths;
- linker search paths and resolved inputs;
- generated `.pyd` dependencies.

Fail if the JIT path invokes or discovers:

- `cl.exe`;
- MSVC `link.exe`;
- `vcvarsall.bat`;
- `vswhere.exe`;
- headers/libraries below Visual Studio;
- headers/libraries below the host Windows Kits/SDK.

Use Clang verbose/`-###` diagnostics and linker tracing. `where.exe` alone is not sufficient proof.

## Implementation result

The initial compatibility proof passes on GitHub `windows-2022` for CPython
3.12, 3.13, and 3.14. The proof compiles and loads a minimal CFFI extension,
then performs a fresh `scripts/test-poisson.py` FFCx JIT and solve with the
setuptools `mingw32` backend and packaged LLVM-MinGW Clang/LLD.

Implementation exposed one additional Windows ABI requirement: the MSVC-built
DOLFINx view of `ufcx_integral` omits the complex tabulation function-pointer
members, while LLVM-MinGW supports C99 complex and includes those members by
default. Without intervention this shifts later fields and DOLFINx reads an
invalid `coordinate_element_hash`. The LLVM-MinGW JIT therefore compiles UFCx
with:

```text
-D__STDC_NO_COMPLEX__
```

This matches FFCx's existing Windows restriction on complex code generation
and keeps the generated UFCx struct layout compatible with the MSVC-built
DOLFINx consumer.

The proof also generates GNU `libpython3.a` / version-named import libraries
whose descriptors target `python3.dll`; PE inspection confirms fresh JIT
modules import `python3.dll` rather than a version-specific Python DLL.

## Exit criteria

Phase 1 is complete when:

- minimal CFFI and FFCx Poisson JIT both compile and load;
- setuptools reports `mingw32`;
- compiler/linker commands use only packaged LLVM-MinGW/LLD;
- no Visual Studio or host Windows SDK headers/libraries participate;
- FFCx uses GNU-driver-compatible flags;
- the Python link strategy is proven on CPython 3.12-3.14;
- fresh Poisson solve succeeds on all supported interpreters;
- compiler/linker/search-path logs are retained as CI artifacts.
