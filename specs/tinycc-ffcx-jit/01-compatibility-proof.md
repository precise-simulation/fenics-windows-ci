# Phase 1: prove TinyCC compatibility

**Status:** proposed.

## Objective

Prove that a pinned x86-64 Windows TinyCC build can compile and load the CFFI extension generated by FFCx, then run the existing Poisson solve, without Visual Studio, host Windows SDK compiler inputs, LLVM-MinGW, GCC, or another linker participating in the JIT process.

This is the primary functional, ABI, CRT, and PE-security go/no-go phase.

## Baselines

Test both:

1. latest formal TinyCC Windows x86-64 release, for reference;
2. a checksum-pinned current upstream development commit, expected to contain newer Win64/PE fixes.

If only the development revision passes, document exactly which upstream changes are required and pin that commit for all later phases.

## Compiler adapter prototype

Do not force TinyCC through setuptools' `mingw32` backend.

Prototype a minimal TinyCC compiler implementation that provides the operations CFFI/build_ext actually needs:

- compile generated `.c` to TCC-owned objects;
- link TCC-owned objects to a `.pyd` using `tcc -shared`;
- translate include dirs, macros, library dirs, and supported extra arguments;
- reject unsupported options and foreign binary inputs instead of silently ignoring important semantics.

Prefer an owned temporary `build_ext` command that directly instantiates `TinyCCCompiler` rather than depending on `new_compiler("tinycc")`. Modern setuptools discovers compiler classes by walking imported subclasses; importing a class is therefore not a truly temporary registration operation even when selection is temporary.

The prototype may still subclass the narrow setuptools/distutils compiler base classes to reuse common compile bookkeeping. Compiler **selection/configuration** must be local to the CFFI Distribution/JIT operation, but the implementation must not claim that importing a TinyCC subclass can be undone globally.

The owned `build_ext` layer must also prevent native-Windows setuptools behavior from adding MSVC/versioned-Python library inputs. If the normal object/link split proves fragile, the fallback is a narrower adapter that invokes TinyCC directly on the generated C sources for the final `.pyd`. Avoid patching global setuptools behavior.

## C language/FFCx flags

FFCx 0.11 requests C17 on Windows using `-std:c17`. Current TinyCC development sources expose C11/gnu11 as the newest explicit language mode and otherwise use older C semantics.

For TinyCC:

- treat C11/default TinyCC mode as the known starting point rather than looking for a nonexistent direct `-std=c17` equivalent;
- compile the exact generated FFCx/CFFI corpus and identify whether it uses any semantics not accepted/correctly implemented by the pinned TinyCC revision;
- remove/translate MSVC- or Clang-specific flags;
- preserve `-D__STDC_NO_COMPLEX__` for the initial proof;
- define `Py_NO_LINK_LIB` for CFFI wrapper compilation where that CPython header feature is supported;
- capture the complete generated C source for every failure;
- treat actually required unsupported C17 semantics as a go/no-go result, not as a reason for broad generated-source rewriting.

## Python Stable ABI

Use the same conceptual ABI strategy as LLVM-MinGW: generated modules import `python3.dll` and must not acquire a minor-version Python dependency through setuptools or CPython headers.

TinyCC's Windows linker supports import definition files directly. Generate/package a deterministic `python3.def` from a supported `python3.dll` export set and pass it explicitly to TinyCC.

The integration must own Python-library selection end-to-end:

- override/suppress setuptools `build_ext.get_libraries()` behavior that would otherwise add `python312`, `python313`, `python314`, or another versioned Python library for a non-MSVC compiler;
- prevent native-Windows setuptools library-directory injection from becoming an accidental source of Python/MSVC link inputs, retaining only explicitly approved library roots;
- define `Py_NO_LINK_LIB` on interpreters where the CPython headers support that switch and independently verify that no header-driven Python autolink dependency is introduced on every supported version;
- pass packaged `python3.def` to TinyCC explicitly;
- reject any versioned Python library name reaching the TinyCC adapter rather than silently accepting it.

Acceptance checks:

- CFFI wrapper compiles with official CPython headers;
- `.pyd` loads on standard GIL-enabled CPython 3.12, 3.13, and 3.14;
- captured compile/link inputs contain no versioned Python library request;
- PE import inspection shows `python3.dll`, not a minor-version DLL;
- the same definition strategy works for all supported interpreters.

Preview standard GIL-enabled Python 3.15 after the supported matrix passes. Free-threaded Python is out of scope for this epic unless it is later added as a separate ABI/import-library qualification target.

## Windows ABI and CRT proof

Record generated-module imports and compare with the LLVM-MinGW reference.

Current upstream TinyCC Win64 links `msvcrt.dll` by default. Treat this as a known Phase-1 issue. Before Phase 2 begins, choose and prove one of these outcomes:

1. **Preferred if practical:** configure/patch the pinned TinyCC runtime so generated modules use the required UCRT-compatible model; or
2. **Mixed-CRT qualification:** retain TinyCC's `msvcrt.dll` runtime but prove that no unsafe ownership or representation crosses between TinyCC-generated code and UCRT/MSVC-built CPython/DOLFINx.

Add an ABI probe compiled by MSVC/LLVM-MinGW and TinyCC that records:

- `sizeof` and alignment of relevant UFCx structs;
- offsets of fields read by DOLFINx;
- function-pointer/calling-convention assumptions;
- sizes/alignment of core integer/pointer/floating types used by UFCx;
- explicit `sizeof(long double)` / `alignof(long double)` and whether any interface actually crosses that representation.

For a mixed CRT, audit and stress any memory, FILE/handle, locale, errno, allocation, string, and error-path ownership that crosses the extension/native boundary. Use Python allocator APIs where generated CFFI wrappers already do so, but do not infer mixed-CRT safety merely from one successful Poisson run.

## PE security and unwind proof

Inspect the emitted `.pyd` beyond import/load success.

For representative minimal CFFI and FFCx modules, record and compare with LLVM-MinGW:

- PE `DllCharacteristics`;
- ASLR/dynamic-base support;
- NX compatibility;
- high-entropy VA on x64 where applicable;
- relocation directory presence/consistency;
- x64 `.pdata`/unwind metadata coverage for generated functions;
- imported system DLLs and unexpected legacy/runtime dependencies.

Current TinyCC sources define relevant mitigation constants but may emit a zero `DLLCHARACTERISTICS` baseline. If the pinned build does not meet the repository's agreed Windows mitigation baseline, require a small pinned source patch and re-run the proof. If acceptable hardened PE output cannot be maintained narrowly, stop the epic.

## Object/library boundary

TinyCC's Windows object model is not interchangeable with normal MSVC/MinGW COFF objects/libraries.

The prototype must reject unsupported foreign link inputs explicitly, including:

- `.lib` files;
- foreign `.obj`/`.o` files;
- arbitrary `.a` archives not produced/qualified for the packaged TinyCC;
- unsupported `extra_objects`;
- arbitrary `cffi_libraries` requests that cannot be satisfied through approved packaged `.def` imports.

Known packaged system/Python `.def` imports and TCC-owned objects/archives are the explicit allowed path. Add at least one negative test in Phase 1 so accidental future pass-through cannot masquerade as support.

## Hermetic proof environment

Reuse the LLVM-MinGW sanitization approach:

- clear VS/MSVC/Windows SDK activation variables;
- remove Visual Studio and Windows Kits paths from `PATH`;
- clear `CC`, `CXX`, `LD`, include/library search variables;
- expose only the TinyCC package/prototype root, active Python/FEniCS runtime DLL paths, and normal Windows system directories;
- clear the TinyCC-specific FFCx cache namespace before each fresh JIT.

CI must fail if the JIT invokes or resolves `cl.exe`, MSVC `link.exe`, Clang, GCC, `vswhere.exe`, or host Windows SDK inputs.

## Tasks

1. Add a manual-only TinyCC experiment workflow on `windows-2022`.
2. Pin and build/download the selected TinyCC x86-64 revision.
3. Implement the smallest prototype TinyCC compiler/build_ext adapter, preferring direct compiler instantiation.
4. Compile/import a minimal CFFI module.
5. Implement the `python3.def` Stable-ABI link path and suppress all implicit versioned Python linking.
6. Translate/reject FFCx compile flags explicitly and prove the generated corpus under TinyCC's available language modes.
7. Run a fresh FFCx Poisson JIT/solve on standard GIL-enabled CPython 3.12-3.14.
8. Run ABI layout probes against the LLVM-MinGW/MSVC reference, including `long double`.
9. Establish either UCRT-compatible TinyCC output or a documented mixed-CRT safety proof.
10. Inspect PE imports, mitigations, relocation/unwind metadata, and retain compile/link/source diagnostics.
11. Add negative foreign-object/library-input tests.
12. Preview standard GIL-enabled CPython 3.15.

## Exit criteria

Phase 1 passes only when all supported Python versions compile, load, and solve correctly with TinyCC as the sole JIT compiler/linker; generated modules import only the intended Stable-ABI Python DLL; no implicit/versioned Python library input participates; the C language, Python/UFCx ABI, `long double` relevance, CRT model, PE mitigation/unwind baseline, and object/library boundary are demonstrated; and no required generated C feature is unsupported.

If this phase needs invasive FFCx source rewriting, cannot establish a safe CRT/ABI boundary, cannot produce an acceptably hardened PE image with a narrow maintainable change, or requires foreign object/library interoperability that TinyCC cannot provide, stop the epic.
